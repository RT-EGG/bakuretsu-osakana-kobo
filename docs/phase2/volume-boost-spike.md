# 500%音量・ピーク抑制スパイク

検証日: 2026-08-01  
対象: `VOL-003`, `SPIKE-003`, `Q-006`

## 1. 目的と安全方針

0～500%のUI範囲に対し、100%超をソフトウェア増幅しながら、デジタル上限を越える
ピークを抑制できる方式を調べる。最初の段階では物理音声デバイスを開かず、人工信号を
WAVへ書き出して数値測定する。無音測定に合格するまで、500%の実音再生は行わない。

検証コードは`spikes/LibVlcVolumeProbe`、確定測定結果は
`.tmp/libvlc-volume-probe-final/volume-probe-report.json`にある。

## 2. ライセンス確認

発行物からGPL-only 4プラグインを除外したLibVLCに対して、既存の自動監査を再実行した。

- 読み取り可能: 319
- 読み取り不能: 0
- GPL-only/AGPL: 0
- 自己申告ライセンス: 全件LGPL 2.1以降

今回調査した`file` audio output、`gain`、`compressor`も、この監査対象に含まれる。
追加のWindows音声出力候補は、正式版`NAudio.Core` 2.3.0と`NAudio.Wasapi` 2.3.0である。
両パッケージはMITを宣言し、`NAudio.Core`は外部依存なし、`NAudio.Wasapi`は同版の
`NAudio.Core`だけに依存する。MIT本文と著作権表示を配布物へ含めれば、MITのままGitHubで
公開・無償配布する方針と両立する。2026-08-01に実時間音声スパイクへ固定追加し、
packages.lock、実物nuspec、SHA-256、出力DLL、MIT本文の同梱を確認した。

## 3. テスト信号と測定方法

48 kHz、2チャンネル、float32の3.2秒WAVを生成した。997 Hz正弦波を次の3レベルで配置した。

| 区間 | 入力レベル | 用途 |
| --- | ---: | --- |
| 0.50～1.30秒 | -30 dBFS | 制限が不要な小信号の増幅率 |
| 1.30～2.10秒 | -12 dBFS | 中レベルでの制限開始 |
| 2.10～2.90秒 | -0.4 dBFS | フルスケール近傍のストレス |

物理出力の代わりに、LibVLCのLGPL `file` audio outputへfloat32 WAVを書き出した。
自作候補は同じ入力へ、チャンネル連動、先読み5 ms、リリース80 ms、上限-1.0 dBFSの
リミッターを適用した。

## 4. 結果

### LibVLC標準経路

- コア`--gain=2`と`--gain=5`は全区間を正確に2倍・5倍へ増幅した。
- -0.4 dBFS入力の最大値は、2倍で1.90999、5倍で4.77496となり、1.0を大幅に超えた。
  コア増幅単独にはピーク保護がなく、そのまま実音出力へ採用できない。
- `file` audio outputは`MediaPlayer.Volume`をサポートせず、設定後の取得値が0となった。
  したがって、この出力を通常の音量APIの検証には使えない。
- 公開APIで適用できるequalizerは動作したが、内部の基準減衰があり、500%の一貫した写像と
  ピーク保護を同時に満たさない。
- `gain`と`compressor`はLGPLだが、今回のLibVLC埋め込み経路では起動引数、メディアオプション、
  一時設定ファイルのいずれでも有効化を確認できなかった。公開APIだけに依存する構成の候補から
  いったん外す。

### 自作リミッター候補

| UI音量 | -30 dBFS区間RMS | 入力比 | 最大ピーク | 1.0超サンプル |
| ---: | ---: | ---: | ---: | ---: |
| 200% | 0.044726 | 2.000倍 | 0.891251 | 0 |
| 500% | 0.111816 | 5.000倍 | 0.891251 | 0 |

自動ゲートは、低レベル区間の要求増幅率誤差0.5%以内、最大-1.0 dBFS以下、範囲外サンプル0を
判定し、200%と500%の両方で合格した。

## 5. 現時点の判断と残課題

DSP単体では、追加ライブラリなしの先読みリミッターを採用候補にできる。ただしこの合格は
実時間出力を保証しない。LibVLCのPCMコールバック、リミッター、Windows音声出力を接続し、
次を確認する必要がある。

1. 物理音量を安全に調整してから、WASAPIレンダーとループバックで処理後ピーク、欠落、連続性を測る。
2. 再生、一時停止、シーク、0.25～2.0倍速、終了、動画切替でバッファと時計を同期させる。
3. A/V同期と音量反映100 ms以内を測る。
4. 自動ゲート合格後だけ、ヘッドホンを使わず、OS・アンプ・スピーカー音量を最小にして
   短時間の聴感確認を行う。

リミッターは過大ピークを防ぐが、500%で常に5倍の知覚音量を保証するものではない。
入力が大きいほどゲインリダクションが働くという`Q-006`の合意範囲に一致する。

## 6. PCMコールバック・実時間バッファ検証

`spikes/LibVlcRealtimeAudioProbe`を追加し、LibVLCの`S16N` PCMコールバックをfloat32へ
明示変換してから、同じ先読みリミッターとNAudioの`BufferedWaveProvider`へ接続した。
WASAPI出力は開かず、100 msプリバッファ後に10 ms周期で消費する模擬レンダーを使用した。

初回実装では自然終了直後の`flush`が末尾約263 msを破棄する問題を検出した。合格判定を撤回し、
`drain`コールバック内で処理待ちサンプルとNAudioバッファを同期排出してから終了するよう修正した。
修正版では自然終了後の`flush`による破棄は0バイトである。

| 素材 | 実行回数 | 合格 | 入力＝制限＝投入＝消費 | 最大ピーク | 非有限値 | underrun / overflow | flush破棄 |
| --- | ---: | ---: | --- | ---: | ---: | ---: | ---: |
| H.264/AAC MP4 1080p/30fps/5秒 | 4 | 4 | 240,640フレーム | 0.891251 | 0 | 0 / 0 | 0 bytes |
| VC-1/WMA Pro WMV 1080p/30fps/5秒 | 4 | 4 | 235,520フレーム | 0.891251 | 0 | 0 / 0 | 0 bytes |

確定レポート例は`.tmp/libvlc-realtime-audio/report-mp4-500-drain2.json`と
`report-wmv-500-drain2.json`にある。追加の反復6件も同ディレクトリに保存した。

この段階で、デコード、500%増幅、リミッター、実時間バッファ、自然終了の連続性は
物理出力なしで合格した。未検証なのは本物のWASAPIレンダー、ループバック波形、A/V同期、
一時停止・シーク・速度変更、実音の聴感である。既定出力は`スピーカー (USBAudio2.0)`であり、
次のゲート前に物理スピーカー音量の安全な調整が必要である。

## 7. WASAPI実出力の安全ゲート

2026-08-01、同プローブに本物のWASAPI共有レンダーと既定出力のループバック計測を追加した。
初回は500%リミッター後へさらに-40 dB（振幅1%）を掛け、再生直前にも既定出力のWindows
マスター音量を読み、5%を超えていてミュートでもない場合は音声出力前に中止する。

最初の試行では`スピーカー (USBAudio2.0)`がWindows音量100%・ミュート解除だったため、
安全ガードが作動した。PCMコールバック、WASAPI出力、ループバックはいずれも開始されず、
音声は出力されていない。記録は`.tmp/libvlc-realtime-audio/wasapi-smoke-mp4-500-minus40.json`にある。
Windowsマスター音量を5%以下へ調整した後、同じ5秒MP4条件から再実行する。

Windows音量を0%へ調整した再試行では、ループバック波形を取得できた。最初の実行は終了直前に
計測タスクをキャンセルして消費フレームを0と記録するハーネス不具合だけで不合格になったため、
計測完了を最大2秒待ってからキャンセルするよう修正した。同じ条件の再実行結果は次のとおりである。

| 項目 | 結果 |
| --- | ---: |
| 入力＝リミッター出力＝バッファ投入＝WASAPI消費 | 240,640フレーム |
| リミッター後ピーク | 0.891251 |
| 追加-40 dB後の出力ピーク | 0.008913 |
| ループバックピーク | 0.008913 |
| 非有限値 / underrun / overflow / flush破棄 | 0 / 0 / 0 / 0 bytes |

自動ゲートは合格した。確定レポートは
`.tmp/libvlc-realtime-audio/wasapi-smoke-mp4-500-minus40-retry.json`である。ループバックは
エンドポイント音量適用前の信号を取得するため、Windows音量0%でも波形を測定できる。一方、物理的な
聴感確認は行えていない。次はWindowsマスター音量を5%にして同じ-40 dB条件を再生する。

続いてWindowsマスター音量5%で同じ5秒MP4を再生した。自動判定は合格し、240,640フレームの
完全消費、出力・ループバックピーク0.008913、非有限値・underrun・overflow・flush破棄0を再確認した。
レポートは`.tmp/libvlc-realtime-audio/wasapi-smoke-mp4-500-minus40-volume5.json`である。
物理スピーカーの音量を十分に絞りすぎていたため、開発者には聞こえず、聴感判定は成立しなかった。
Windows音量5%と追加-40 dBを維持し、物理スピーカーだけを普段の低めの聴取位置へ少し上げて再確認する。

物理スピーカー調整後の再確認も自動ゲートに合格した。全240,640フレームを消費し、出力・
ループバックピーク0.008913、非有限値・underrun・overflow・flush破棄0だった。レポートは
`.tmp/libvlc-realtime-audio/wasapi-smoke-mp4-500-minus40-volume5-audible.json`である。
この実行の聴感結果は開発者回答待ちである。

開発者には-40 dB条件の音が聞こえなかったため、Windows音量5%と物理スピーカー位置を維持し、
追加減衰だけを-30 dBへ一段緩めた。全240,640フレームを消費し、出力・ループバックピークは
理論値どおり0.028184、非有限値・underrun・overflow・flush破棄は0だった。

初回の自動判定だけは、-40 dB段階用に固定していたループバック上限0.02を超えたとして不合格にした。
これは波形異常ではなく判定ハーネスの追従漏れである。指定した減衰量から求めた理論ピーク上限へ
連動するよう修正した。初回レポートは
`.tmp/libvlc-realtime-audio/wasapi-smoke-mp4-500-minus30-volume5.json`であり、-30 dBの聴感結果は
開発者回答待ちである。

-20 dB条件も開発者には聞こえなかった。短い5秒試行で物理スピーカーを調整することが難しいため、
Windows音量5%・追加-20 dBを維持し、残り時間と停止ボタンを表示する30秒校正モードを次に用意する。
実装前に、音声を出さない10秒間のWinFormsウィンドウ表示テストを行い、Codex実行セッションから
対話デスクトップへ表示できることを開発者が確認した。

`Run-Calibration.ps1`を追加し、3秒カウントダウン、残り時間、現在の安全条件、停止ボタンを持つ
校正ウィンドウを用意した。停止ボタンまたはウィンドウを閉じた場合は音声プロセスを終了する。
既存の1分MP4を使い、Windows音量5%・追加-20 dBを固定したまま、再生中に物理スピーカーを
徐々に調整する。プローブのWASAPI実測タイムアウトも1分素材に対応する75秒へ延長した。

1分校正を実行し、自動ゲートに合格した。全2,880,512フレームを消費し、出力・ループバック
ピーク0.089125、非有限値・underrun・overflow・flush破棄0だった。レポートは
`.tmp/libvlc-realtime-audio/wasapi-calibration-mp4-500-minus20-volume5-60s.json`である。
校正中の聞こえ方と物理スピーカー調整結果は開発者回答待ちである。

開発者は物理スピーカーを通常位置に戻し、再生中にWindows音量を約70%まで上げた時点で
聞き取れることを確認した。不快な大きさ、音割れ、音切れはなく、停止ボタンも不要だった。
追加-20 dB・Windows音量70%の振幅係数は概算0.07である。次にWindows音量を5%へ戻して
追加減衰を0 dBにすると係数は概算0.05となり、校正時より約3 dB小さいまま、本来の500%処理を
確認できる。

今回、開始後にWindows音量を5%から70%へ変更できたため、安全ガードが開始時だけであることも
確認した。再生中も100 ms周期で既定出力音量を監視し、5%を超えてミュートでもない場合は
自動停止して不合格を記録するよう改善し、警告・エラー0でビルドした。

Windows音量を5%へ戻し、物理スピーカーを通常位置のまま、追加減衰0 dBで本来の500%処理を
MP4 5秒へ適用した。自動ゲートは合格し、全240,640フレームを消費、出力・ループバックピークは
0.891251（-1 dBFS）、非有限値・underrun・overflow・flush破棄0だった。開始時と再生中の
Windows音量は5%を維持し、安全停止は発生していない。レポートは
`.tmp/libvlc-realtime-audio/wasapi-smoke-mp4-500-0db-volume5.json`である。聴感結果は開発者回答待ち。

この5秒試行は開発者には聞こえなかった。追加減衰0 dBを維持したままWindows音量だけを5%から
徐々に調整できるよう、校正スクリプトとプローブへWindows音量の安全上限引数を追加した。次回は
上限10%とし、100 ms周期の監視で10%超過時に自動停止する。物理スピーカーは通常位置を維持する。

開発者指定により校正上限を50%へ変更した。初回はWindows音量53%を検出して自動停止したため、
上限監視が機能することを確認した。一方、音量上限を第6引数として追加した際、減衰の第5引数を
`args.Length == 5`でのみ読む実装になっており、追加0 dB指定が既定-40 dBへ戻る不具合を検出した。
この実行は0 dB試験として無効とし、条件を`args.Length >= 5`へ修正した。レポートは
`.tmp/libvlc-realtime-audio/wasapi-calibration-mp4-500-0db-max50-60s.json`である。

修正後、追加0 dB・Windows音量上限50%の1分校正を再実行し、自動ゲートに合格した。
全2,880,512フレームを消費し、出力・ループバックピーク0.891251（-1 dBFS）、非有限値・
underrun・overflow・flush破棄0だった。Windows音量は計測開始時24%、最大50%で、安全停止は
発生していない。レポートは
`.tmp/libvlc-realtime-audio/wasapi-calibration-mp4-500-0db-max50-60s-retry.json`である。

開発者はWindows音量約20%から聞こえ始め、50%でちょうどよい音量と確認した。不快な大きさ、
音割れ、音切れはなく、停止も不要だった。これによりMP4の追加減衰なし500%実出力は、数値と
聴感の両方で合格とする。

同じ追加0 dB・Windows50%でWMV 5秒も測定し、自動ゲートに合格した。全235,520フレームを
消費し、出力・ループバックピーク0.891251、非有限値・underrun・overflow・flush破棄0だった。
レポートは`.tmp/libvlc-realtime-audio/wasapi-smoke-wmv-500-0db-volume50.json`である。

WMVもWindows音量50%でちょうどよく、不快な大きさ、音割れ、音切れなしと開発者が確認した。
これによりMP4とWMVの追加減衰なし500%実出力は、自動測定と聴感の両方で合格した。

## 8. 操作遷移

同期専用MP4で、一時停止、再開、50%シーク、1.5倍速、1.0倍速復帰を自動実行した。シーク直後は
WASAPIが1回無音読み出ししたため、flush後に100 msを再プリバッファしてから再開するよう修正した。
シークで正しく破棄される先読み240フレームを明示計上し、WASAPI読み出しとバッファクリアも
同じロックで直列化した。

最終実行は合格し、停止中PCM callback 0、pause/resume callback確認、シークflush 2回、
シーク後5752 ms到達、速度実値1.5/1.0、underrun/overflow 0、ループバックピーク0.891251だった。
レポートは`.tmp/libvlc-realtime-audio/wasapi-transitions-mp4-500-0db-volume50-final2.json`である。

途中でループバックに0.96～0.99の別音声が混入したが、操作なし・追加-40 dBの再測定と音声
セッション監査では出力・ループバック0.008913が一致した。混入消失後の最終シナリオでは
出力・ループバック0.891251が一致したため、候補経路のピークではない。

-30 dB条件も開発者には聞こえなかったため、Windows音量5%と物理スピーカー位置を維持し、
追加減衰だけを-20 dBへ一段緩めた。この実行は自動ゲートに合格し、全240,640フレームを消費、
出力・ループバックピーク0.089125、非有限値・underrun・overflow・flush破棄0だった。レポートは
`.tmp/libvlc-realtime-audio/wasapi-smoke-mp4-500-minus20-volume5.json`であり、聴感結果は
開発者回答待ちである。

同じPCM callback・リミッター・WASAPI経路を維持し、同期専用MP4の映像をLibVLCのD3D11VAで
表示する10秒モードを追加した。自動ゲートは合格し、全480,256音声フレームを消費、出力・
ループバックピーク0.891251、非有限値・underrun・overflow・flush破棄0だった。レポートは
`.tmp/libvlc-realtime-audio/wasapi-avsync-video-mp4-500-0db-volume50.json`である。映像マーカーと
音声パルスの実画面同期は開発者回答待ちである。

開発者が映像ウィンドウの表示を確認し、映像マーカーと音声パルスに目立つずれはなかった。
これにより500%音量スパイクは、MP4/WMV、ピーク抑制、WASAPI実出力、聴感、操作遷移、
A/V同期の検証を完了した。Phase 4ではこの候補方式を本実装へ移植し、自動テストを整備する。
