# 速度切替直後の音飛び調査

調査日: 2026-08-03  
対象: LibVLC 3.0.23 / LibVLCSharp 3.10.0 / NAudio PCMコールバック経路

## 結論

速度切替後の定常再生品質はMP4、WMVとも主観合格しているが、切替直後の音飛びを
**完全になくせるとは現構成では保証できない**。速度要求はLibVLCへ100 ms以内に反映される一方、
音声PCMコールバックの供給間隔が一時的に約100～1,000 msまで開く。100 msのNAudio先読みでは、
すべての切替を吸収できなかった。

ピッチ維持用`scaletempo`の設定短縮および無効化でも改善しなかったため、原因は同フィルターだけではなく、
LibVLCの速度変更時の入力クロック・音声出力同期を含む経路にあると判断する。UIや
`MediaPlayer.SetRate`呼出し箇所だけの局所修正で、シームレスな切替を保証できる問題ではない。

ただし、アプリ全体を作り直す必要が確定したわけではない。Phase 4で再生バックエンドとUIを分離し、
速度変更と音声出力を境界の内側へ閉じ込めれば、将来必要になった場合も、音声処理層または
再生バックエンドだけを差し替えられる。

2026-08-03の開発者判断により、再生速度変更の重要度を下げ、切替直後の音飛びを既知制約として
許容する。シームレス切替を保証せず、本件の追加調査、LibVLC独自修正、代替バックエンド比較は
行わない。

## 再現と計測

`LibVlcRealtimeAudioProbe`へ`rate-transitions`シナリオを追加し、次の順で各750 ms再生した。

`1.0 → 0.25 → 1.0 → 0.5 → 1.0 → 2.0 → 1.0`

1080p/30fps H.264/AAC MP4を、WASAPIへ出さない模擬コンシューマーと100 ms先読みで測定した。

| 切替 | 通常: 最大PCM間隔 | `scaletempo`無効: 最大PCM間隔 |
| --- | ---: | ---: |
| 1.0 → 0.25 | 984 ms | 983 ms |
| 0.25 → 1.0 | 248 ms | 249 ms |
| 1.0 → 0.5 | 494 ms | 487 ms |
| 0.5 → 1.0 | 254 ms | 262 ms |
| 1.0 → 2.0 | 124 ms | 124 ms |
| 2.0 → 1.0 | 247 ms | 246 ms |

通常、無効の両条件で、10 ms単位の模擬消費に対する先読み後アンダーランは49回だった。
これはプローブ自体の失敗ではなく、100 msバッファでは供給停止を隠せないという測定結果である。
WMVでも同じ傾向を確認し、最大PCM間隔はおおむね100～500 msだった。

低遅延設定（stride 10 ms、search 3 ms）も通常設定と実質同じだった。通常ログでは
`scaletempo`の選択と既定値（stride 30 ms、overlap 20%、search 14 ms）を確認し、無効化ログでは
同フィルターが選択されていないことを確認した。それでも結果が変わらないため、単純な
`scaletempo`パラメーター調整は解決策にならない。

測定レポートは`.tmp/libvlc-rate-transitions/`へ出力する。再現コマンドと引数は
`spikes/LibVlcRealtimeAudioProbe/README.md`を参照する。

## 実装・上流の根拠

- LibVLC 3.0.23の`lib/media_player.c`は速度を入力へ設定するが、切替音声を連続化するAPIは提供しない。
- `src/input/input.c`では速度変更時に入力、クロック、ES出力へ新しい速度を伝播する。
- `modules/audio_filter/scaletempo.c`は1.0倍で処理を迂回し、非1.0倍では内部キューを使う。ただし、
  今回は同フィルターを無効にしてもPCM供給間隔が改善しなかった。
- VideoLANには同症状の公式issue
  [#25056: Stutter in audio when changing playback speed](https://code.videolan.org/videolan/vlc/-/issues/25056)
  があり、速度変更時の約0.1秒のstutterとaudio outputのlate/early補正が報告されている。
  2026-08-03時点でopen、milestoneなし、関連merge request 0件である。
- VLCの現行masterでも`scaletempo`の基本的な切替方式は同様であり、既知の解消版があるとは確認できなかった。

## 解決策候補と影響

| 方針 | 期待できること | 主な影響 |
| --- | --- | --- |
| 既知制約として許容 | 現構成を維持し、定常再生品質を利用できる | 長押し2倍速を含め、切替直後の短い音飛びは残る可能性がある |
| LibVLCを維持して独自対策 | クロスフェード、明示的な一時停止、独自tempo処理等を試せる | 無音区間を隠すだけでは完全解消にならない。映像クロックとの同期、追加ライブラリのライセンス監査が必要 |
| LibVLCを修正 | 原因層で改善できる可能性がある | LibVLC fork、Windowsビルド、回帰試験、対応ソース配布を継続保守する必要がある |
| 再生バックエンドを比較・変更 | 別実装で滑らかな切替を得られる可能性がある | mp4/wmv、500%音量、サムネイル、GPU、配布物、LGPL条件を再検証する必要がある |

単純にバッファを約1秒へ増やす案は、操作から音が聞こえるまでの遅延とA/V同期調整を新たに生むため
推奨しない。短いフェードはクリックを弱められても、PCMが供給されない時間そのものは埋められない。

## Phase 2での決定

初回最小リリースには速度変更を含めないため、初回版の実装開始を直接止める問題ではない。
後続機能の長押し2倍速を含め、切替直後の短い音飛びは許容する。受け入れ確認では、各速度での
継続再生中に目立つ音切れ、不自然なピッチ変化、A/Vずれがないことを確認する。切替の瞬間に
シームレスであることは合否条件にしない。本件はPhase 2の阻害事項から外し、追加調査を終了する。
