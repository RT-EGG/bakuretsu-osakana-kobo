# LibVLC代表動画バックエンド検証

最終更新日: 2026-07-29  
状態: 自動バックエンド検証完了、WPF実描画・出力経路確認済み、聴取確認待ち  
実装: `spikes/LibVlcPlaybackProbe`  
全件結果: `docs/phase2/results/libvlc-playback-probe.json`  
反復結果: `docs/phase2/results/libvlc-seek-repeat-summary.json`

## 1. 結論

H.264/AAC MP4 8本とVC-1/WMA 9 Professional WMV 8本の計16本について、LibVLC 3.0.23で
次の自動バックエンド検証がすべて成功した。

- メディア解析とコーデック、解像度、30/60 fps、長さ、48 kHzステレオの認識
- 再生開始と再生時計の進行
- デコード済み映像フレームと音声サンプルのコールバック到達
- 一時停止中の時計停止と再開
- 中間位置と末尾1秒前へのシーク後、3フレーム以上のデコードと時計進行
- 60秒素材で0.25、0.5、1.0、1.5、2.0倍速要求の受理

したがって、LibVLCバックエンドは両コンテナ・代表コーデックを機能上扱える。ただし4K WMVの
シークには再現性のある大きな遅延があり、1080p WMVと同じ性能保証にはできない。

## 2. 条件と限界

| 項目 | 条件 |
| --- | --- |
| OS | Microsoft Windows 10.0.26220（Windows 11系ビルド） |
| ランタイム | .NET 10.0.9、x64 |
| 論理プロセッサ数 | 24 |
| LibVLC | 3.0.23 Vetinari |
| LibVLCSharp | 3.10.0 |
| VideoLAN.LibVLC.Windows | 3.0.23.1、GPL-onlyプラグイン4件を除外 |
| デコード | `--avcodec-hw=none` によるソフトウェアデコード |
| 出力 | RV32映像コールバック、S16N 48 kHz stereo音声コールバック |
| キャッシュ | file caching 150 ms |

この測定は、コーデックを実際にデコードできることを画面や音声機器に依存せず確認する
バックエンド・ゲートである。WPF `VideoView`、GPUデコード、実音声出力、A/V同期の目視・聴取、
主観的な速度別音質は含まない。コールドスタートや製品性能の目標値としては使用しない。

音声コールバック出力はLibVLCの通常オーディオミキサーを経由しないため、同ハーネスで音量APIを
設定すると実値0%を返す。0～500%要求、実効増幅、ピーク抑制はWPFの通常音声出力と別の
増幅・リミッター経路で検証する。

## 3. 全16本の結果

全16本が合格し、実行時間は約63秒だった。時間は1回のウォーム実行であり、採用性能値ではない。

| コンテナ | 解像度 | 本数 | 最初の映像フレーム | 中間シーク | 末尾シーク |
| --- | --- | ---: | ---: | ---: | ---: |
| MP4 | 1920x1080 | 4 | 643～817 ms | 281～358 ms | 288～389 ms |
| MP4 | 3840x2160 | 4 | 819～870 ms | 362～420 ms | 346～520 ms |
| WMV | 1920x1080 | 4 | 861～1099 ms | 360～1170 ms | 626～1319 ms |
| WMV | 3840x2160 | 4 | 1132～1207 ms | 1312～4492 ms | 1836～5183 ms |

シーク成功は、`MediaPlayer.Time`の即時変化だけでは判定していない。指定位置から時計が100 ms以上
進み、シーク要求後に3フレーム以上が映像コールバックへ到達することを必須とした。

## 4. 4K長尺WMVの5回測定

3840x2160、60秒のWMVについて、全件実行1回と単独反復4回を合わせて測定した。

| fps | 最初の映像フレーム 中央値/最大 | 中間シーク 中央値/最大 | 末尾シーク 中央値/最大 |
| ---: | ---: | ---: | ---: |
| 30 | 871 / 1132 ms | 2131 / 2341 ms | 2728 / 2753 ms |
| 60 | 1159 / 1169 ms | 4442 / 4492 ms | 4972 / 5183 ms |

4K60 WMVはすべて機能上成功したが、シーク応答は約4～5秒である。初回リリースでWMVを保証する
場合は、まず1080pを保証範囲とし、4K WMVを性能保証外またはベストエフォートにする案を推奨する。
最終決定はWPF/GPU経路の実機測定後に開発者が行う。

## 5. LibVLC診断ログ

`EncounteredError`は全件で発生せず、検証条件もすべて満たした。一方、ログには次が残った。

- コールバック出力にウィンドウハンドルがないことによる `Failed to set on top`
- 一部の色変換候補が使えないことを示す `Failed to create video converter`
- MP4のedit list/STTS情報
- ASFオブジェクト読取警告
- 高負荷WMVシーク時のlate buffer/drop
- 急速な停止・シーク時のreference clock/timestamp変換失敗

映像・音声コールバックと再生時計は継続したため、自動ゲートでは非致命診断として記録した。
ただしWPF実出力でも同じtimestamp、drop、converterログが再現するか確認し、再現時はフレーム落ち、
A/V同期、シーク後の表示内容を目視・聴取して判定する。

## 6. ライセンスゲート

検証ハーネスの直接NuGet依存は `LibVLCSharp` 3.10.0と
`VideoLAN.LibVLC.Windows` 3.0.23.1だけである。WPFスパイクと同じ4件を除外したRelease出力で、
プラグイン319件の自己申告ライセンスを検査し、読取不能0件、GPL-only 0件を確認した。
ハーネスはアプリの採用依存を追加しない。

## 7. 次の検証

1. WPF `VideoView`と通常音声出力で、MP4/WMVの映像、左右音、同期パルスを目視・聴取する。
2. ハードウェアデコード有効時に各条件を5回測定し、UI上の初回フレームとシーク応答を記録する。
3. 4K WMVの保証範囲を、実機結果と利用想定に基づいて決定する。
4. 0.25～2.0倍速の音質・ピッチ・A/V同期を聴取する。
5. 100～500%増幅とピーク抑制方式を実装・測定する。
6. HEVC、VFR、破損、非対応素材を追加してエラー分類を検証する。
