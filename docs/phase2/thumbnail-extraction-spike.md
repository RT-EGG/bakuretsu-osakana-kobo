# 任意位置フレーム取得スパイク

最終更新日: 2026-08-02  
状態: Phase 2スパイク合格

## 1. 候補方式

監査済みのLibVLCSharp / LibVLCだけを使用し、主再生とは別の`MediaPlayer`で映像callbackを受ける。
追加画像ライブラリは導入せず、検証画像はBGRAからBMPへ直接保存した。本実装では320px幅へ縮小し、
動画を開いているセッション中だけメモリキャッシュする候補とする。

## 2. 単発取得

60秒素材の0%・50%・90%を取得した。シーク時計が対象へ到達してから次フレームを要求し、
シーク前の旧フレームを拾わないようにする必要がある。

| 素材 | 初回 | 50% | 90% | 最大時刻差 | Working Set |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1080p/30fps | 679 ms | 72 ms | 71 ms | 10 ms | 123 MiB |
| 4K/60fps | 953 ms | 381 ms | 394 ms | 10 ms | 289 MiB |

画像を目視し、動画内表示の0秒・30秒・54秒と一致することを確認した。

## 3. 1%間隔100枚

320px幅へ縮小して0～99%を生成した。

| 素材 | 全体時間 | 通常の1枚 | 最大時刻差 | CPU時間 | Working Set |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1080p/30fps | 4.7秒 | 3～67 ms | 10 ms | 7.7秒 | 77 MiB |
| 4K/60fps | 14.9秒 | 3～281 ms | 610 ms | 60.7秒 | 71 MiB |

全100画像は相互に異なり、2秒以内の仮基準を満たした。4KではCPU時間が平均約4コア相当となるため、
無制限の連続生成は採用しない。1080p高速連続シークではLibVLCの`buffer deadlock prevented`警告も
発生したため、逐次・低優先度・要求間隔ありとし、再生操作中はバックグラウンド生成を止める。

## 4. 主再生との競合

4K/60fps WPF主再生を単独測定後、開始2秒後から低優先度の4Kサムネイル100枚を併走させた。
主再生は両方ともD3D11VAを維持し、性能シナリオに合格した。

| 指標 | 単独 | 併走 | 差 |
| --- | ---: | ---: | ---: |
| 最初の再生時計 | 425.6 ms | 424.2 ms | -1.4 ms |
| Video Output | 180.2 ms | 183.6 ms | +3.4 ms |
| 50%シーク | 467.6 ms | 462.6 ms | -5.0 ms |
| 90%シーク | 1095.5 ms | 1072.1 ms | -23.4 ms |

この基準PCでは、別ワーカーを低優先度にすることで主再生への有意な悪化はなかった。

## 5. ホバー優先と動画切替

低優先度4K 100枚生成中に、通常優先度で77%位置を割り込ませた。実取得259 ms、ワーカー起動込み
977 msで合格した。続いて旧動画ワーカーを12枚時点で終了すると60 msで停止し、新しい1080p動画の
25%位置は実取得205 ms、起動込み858 msで取得できた。

Phase 4では単一アプリプロセス要件を維持するため、同じ考え方を専用バックグラウンドサービスと
別`MediaPlayer`へ移植する。キューは逐次処理し、ホバー要求を先頭へ入れ、動画切替時は現行playerを
停止・破棄してキャッシュをクリアする。今回の別プロセス試験は負荷分離・優先・強制キャンセルの
実現性確認であり、本番で子プロセスを採用する決定ではない。

## 6. ライセンス

追加ライブラリはない。`LibVLCSharp` 3.10.0と`VideoLAN.LibVLC.Windows` 3.0.23.1だけを使用する。
Release出力は既存監査と同じ319プラグイン、除外対象GPLプラグイン一致0件だった。

レポートは`.tmp/libvlc-thumbnails/`、スパイクは`spikes/LibVlcThumbnailProbe`にある。
