# WPF実画面・通常音声出力検証

最終更新日: 2026-08-02  
状態: MP4・1080p WMVの基本再生・速度別主観品質ゲート完了

## 1. 結論

WPF `VideoView`の実描画で、次の代表条件を画面キャプチャし、動画内の解像度・fps表示、
フレーム番号、時刻、グリッド、色票、移動図形が描画されることを確認した。

- 1920x1080 / 60秒 / 60fps H.264/AAC MP4
- 1920x1080 / 60秒 / 60fps VC-1/WMA 9 Professional WMV
- 3840x2160 / 60秒 / 60fps H.264/AAC MP4
- 3840x2160 / 60秒 / 30fps VC-1/WMA 9 Professional WMV

いずれもキャプチャ時にWPFプロセスは応答状態を維持した。LibVLCログでは、通常音声出力として
`mmdevice`とWASAPIが開始された。

ハードウェアデコードには明確な差があった。

| 条件 | 映像デコード結果 |
| --- | --- |
| 4K/60fps H.264 MP4 | RTX 3070 TiのD3D11VAを使用 |
| 1080p/60fps VC-1 WMV | RTX 3070 TiのD3D11VAを使用 |
| 4K/30fps VC-1 WMV | D3D11VAとDXVA2が4K VC-1構成を受理せず、ソフトウェアデコードへフォールバック |

この結果は、既存の4K WMVシーク遅延と整合する。4K WMVは30fpsを含めて初回性能保証から
外し、1080pまでをWMVの初回保証範囲とする。2026-07-30に開発者確認済み。

## 2. 操作確認

WPF UI Automationを介して、実際の画面コントロールとイベント経路を確認した。

- 自動再生後、時刻表示が進む。
- 一時停止中は時刻表示が停止し、再開後に再び進む。
- 0.25、0.5、1.0、1.5、2.0倍の各項目を選択でき、変更失敗表示は発生しない。
- 音量0、100、200、500%要求は、非再生時のLibVLC実値としてそれぞれ同値まで反映される。

音量実値は設定直後には一つ前の値を返すため、UIを200ミリ秒タイマーで再取得するよう修正した。
これにより各要求値と実値が一致することを確認した。500%での実音声再生は聴覚安全とピーク抑制が
未実装のため、この検証では行っていない。

## 3. 測定環境と方法

| 項目 | 値 |
| --- | --- |
| OS | Microsoft Windows 10.0.26220（Windows 11系ビルド） |
| .NET Runtime | 10.0.9 |
| アーキテクチャ | x64 |
| 論理プロセッサ | 24 |
| GPU | NVIDIA GeForce RTX 3070 Ti |
| 映像出力 | LibVLC `direct3d11`からWPF `VideoView` |
| 音声出力 | LibVLC `mmdevice` / WASAPI |

`scripts/capture-wpf-playback-frame.ps1`が、動画を起動引数で開き、WPFウィンドウの実描画を
`PrintWindow`で取得する。`BOK_WPF_VLC_LOG`を指定した場合は、LibVLCの選択した映像・音声経路を
記録する。

## 4. 残る手動確認

2026-07-29に開発者が1080p/60fpsのWMV、MP4を聴取し、次を確認した。

- 左から低い440 Hz、右から高い660 Hzが聞こえる。
- 0.5秒ごとの短い左右交互パルスが聞こえる。
- 音切れはない。
- 他の動画プレイヤーと比較して音の発生タイミングは同等で、少なくとも明らかなA/Vずれはない。

現行素材は音声パルスと同時に点灯する映像マーカーを持たないため、明らかなずれがないことを
超える厳密な同期判定には使えない。これはプレイヤーの不合格ではなくテスト素材の不備として扱う。
次回素材では、最初の同期イベントを0.5秒以降に置き、各パルスと同時に左右別の画面領域を
点灯させる。

先頭へシークして再生し直した際、最初の音がわずかに欠けた可能性が開発者から報告された。
現行素材の最初の50ミリ秒パルスは時刻0から始まるため、シーク後のデコーダー・音声出力の
立ち上がりと重なって判定できなかった。Phase 2の技術選定を止める問題とはせず、修正版素材で
次を再確認し、いずれも目立った問題がないことを2026-07-30に確認した。

1. 先頭シーク後、0.5秒以降の最初の同期イベントが欠けない。
2. 0.25～2.0倍速で許容できない音切れ、ピッチ変化、映像とのずれがない。
3. 一時停止、再開、中間・末尾シーク後も左右音と同期が保たれる。

500%音量とピーク抑制は別スパイクで安全な方式を実装してから聴取する。

## 5. 同期専用素材

2026-07-29に、現行素材の判定不能を解消する10秒・1080p/60fpsの同期専用MP4とWMVを作成した。

- 0.0～0.5秒: 無音プリロール
- 0.5、1.5、2.5秒…: 左1 kHzパルスと画面左半分の黄色点灯
- 1.0、2.0、3.0秒…: 右1.5 kHzパルスと画面右半分のシアン点灯
- パルスと点灯の長さ: 80ミリ秒

FFmpegデコードによる区間測定では、プリロールが左右とも-91.0 dB、左イベントが左-0.6 dB・
右-21.9 dB、右イベントが左-21.9 dB・右-0.6 dBだった。MP4、WMVの双方で同じ関係を確認した。
映像も0.5秒で左、1.0秒で右が全面点灯する。

LibVLCバックエンド検証は2本とも合格した。WPF実出力でも両方がD3D11VAとWASAPIを使用し、
プロセスは応答状態を維持した。WMVのWPFキャプチャでは1.067秒の右点灯フレームを取得した。
2026-07-30に開発者が同期専用WMVとMP4をWPFで確認し、パルスと点灯の同時性、および
先頭シーク後の最初の0.5秒イベントに目立った問題がないことを確認した。これにより、
MP4は4K/60fpsまで、WMVは1080p/60fpsまでの基本再生ゲートを完了した。

## 6. 速度別主観品質

2026-08-02に開発者が同期専用MP4とWMVをWPF実画面・通常音声出力で再確認した。
1.0倍を基準とし、0.25、0.5、2.0倍で左右の点灯・音声パルスを確認した結果、両形式とも
継続再生中に目立つ音切れ、不自然なピッチ変化、A/Vずれはなく、主観品質ゲートに合格した。

再生中に速度を変更した直後だけ短い音飛びが再現した。当初は既知挙動として許容したが、
将来の方式変更リスクを確認するため2026-08-03に再調査した。PCM計測では1.0↔2.0倍でも
約100～250 ms、低速側では最大約1,000 msの供給間隔が生じ、100 ms先読み、`scaletempo`の
低遅延化・無効化では解消しなかった。2026-08-03の開発者判断により再生速度の重要度を下げ、
定常品質の主観合格を維持したまま、切替直後の音飛びを既知制約として許容する。シームレスな切替を
保証せず、本件の追加調査は行わない。詳細は`docs/phase2/rate-transition-investigation.md`を参照する。

検証中、再生終了後にシークバーを左端へ動かしても再開できず、10秒弱の全体時間が9秒へ
切り捨て表示されるスパイクUI上の問題が見つかった。品質判定と切り離すため、「先頭から」で
メディアを再オープンする操作と、全体時間を秒単位で切り上げ表示する処理を追加し、Release buildが
警告0・エラー0で成功した修正版を使って速度別確認をやり直した。
