# v1.1.1 音量・ミュート可聴反映遅延 基準調査

最終更新日: 2026-09-01
状態: 基準調査・修正実装完了、広範な実音声回帰待ち

## 目的

`VOL-008`の受け入れ条件に従い、再生中の音量変更、ミュート、ミュート解除について、WPF操作からバックエンド値更新、処理済みPCMキュー深度、実WASAPIループバック出力の遷移までを同一タイムラインで測る。

## 2026-09-01時点の確認

- `RealtimeAudioOutput`は`S16N` 48 kHz/2ch入力をゲイン・ミュート・リミッター処理した後、最大2秒の`BufferedWaveProvider`へ格納する。
- 音量・ミュート変更は`RealtimeVolumeProcessor`の新しい入力へ直ちに適用されるが、キュー内の変更前処理済みPCMはそのままWASAPIへ読み出される。このため、キュー深度に近い可聴遅延が生じる構造である。
- 音量・ミュート操作時のキュー量をbytesと48 kHz stereo float換算millisecondsで`RealtimeAudioDiagnostics`へ記録する計測点を追加した。
- `BOK_AUDIO_LATENCY_VALIDATION=1`の実WPF検証モードを追加した。ミュートボタンと音量スライダーを実際のWPFイベント経路で操作し、バックエンド値更新時間、操作時キュー深度、WASAPI loopbackのRMS遷移時間をJSONへ記録する。
- 検証モードは既定出力のミュート解除と物理音量50%以下を開始条件とし、条件外では増幅音声を出さず停止する。

## 測定条件

- 既定出力: `スピーカー (USBAudio2.0)`、50%、非ミュート。
- loopback形式: IEEE float 32-bit、48 kHz、2ch。
- 素材: 保証対象の1920x1080・60秒・30fps H.264/AAC MP4とVC-1/WMA 9 Professional WMV。
- 各形式3回。各回で100%ミュート解除・ミュート、25%ミュート解除・ミュート、25%から500%、500%から25%を実WPFコントロール経由で操作した。
- 音量遷移は素材内の短い周期パルスを誤認しないよう、8 loopback block連続で新レベルを満たした場合に確定し、連続区間の先頭blockを遷移時刻とした。
- 初回は既定出力100%を安全ガードが検出して停止した。また、初期の2 block判定ではWMVの周期パルスを500%遷移と誤認する試行が1件あり、いずれも最終基準値から除外した。

## 修正方式の比較

### バッファ短縮

現在の2秒は容量上限であり、実際の定常キューは約1.1～1.35秒だった。容量だけを100 ms未満へ下げると、先行して届くLibVLC callbackを`DiscardOnBufferOverflow=false`のまま受けられずoverflowとなる。callbackの長時間block、古い音声のdrop、変更時の全clearはいずれも、native callback停滞、目立つ音切れ、約1秒の音声破棄、再buffer、A/V同期ずれを生む可能性が高い。100 ms目標の主方式としては推奨しない。

### レンダー読出し段での適用

有界キューにはゲイン適用前のPCMを保持し、WASAPIが読み出す直前に現在の音量・ミュートと100%超の先読みリミッターを適用する。既存の約1秒キューとA/V時系列を維持しながら、操作後に新しく読み出すsampleからレベルを変えられるため、50 ms WASAPI latencyと5 ms lookaheadを含めても100 ms目標へ到達できる見込みがある。

実装では、raw float PCMの有界所有権、`IWaveProvider.Read`が要求長を満たすための小さい処理後staging、5 ms limiter pending、自然終了時drain、seek/rate変更時flush、pause/rebuffer、callback停止後の破棄順を一体で設計する必要がある。単純に現在の処理済みbufferへ追加のgainを掛ける方式は旧gainを元へ戻せず、500%リミッターも二重化するため採用しない。

推奨案は、キュー容量とproducer/consumer関係を維持したまま、`RealtimeVolumeProcessor`をWASAPI pull側へ移し、raw PCMキューと少量の処理後stagingを持つ方式である。
