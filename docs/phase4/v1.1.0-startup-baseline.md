# v1.1.0 起動区間計測と改善結果

測定日: 2026-08-29～2026-08-30

対象: `NEXT-START-001`, `NEXT-START-002`

生データ: `docs/phase4/results/v1.1.0-startup-baseline.json`

## 1. 測定方法

- framework-dependent `win-x64`の製品発行物を一意な一時ディレクトリへ生成し、条件ごとに別プロセスで5回起動した。
- `BOK_STARTUP_TRACE_PATH`が指定された測定時だけ、製品`App.OnStartup`が単調増加時計で区間を記録する。通常起動では計測器を生成しない。
- シェル操作可能点は、空のWindowが`ContentRendered`とDispatcher `ApplicationIdle`へ到達した時点とした。完全初期化点は、シェル操作可能、初回起動要求完了、非ブロッキング自動更新確認開始がすべて完了した時点とした。
- 改善版はシェル操作可能点まで再生・永続化操作を無効表示し、その後に更新結果と4つの永続Repositoryを並列に読み、LibVLCをUIスレッド外で初期化する。完了後だけDispatcher上でサービスを接続し、初回起動要求と二次IPC要求を既存FIFOキューから処理する。
- `first-empty`は各回で`data`を削除する。`existing-empty`は4つの有効なschema 1文書を空データで用意する。`existing-file-muted`は同じ4文書と100%ミュートの動画プロファイルを用意し、5秒H.264/AAC MP4を起動引数で渡す。
- 各プロセス終了後は1秒待つ。ファイル引数条件は計測後に5秒安定待ちしてから通常終了する。OSファイルキャッシュは消去しないため、ハードウェアの完全コールドブートではなく、別プロセス・新規発行先によるコールド相当測定である。

シェル操作可能中央値は808.41 ms以下、15回の最大も新規発行先初回の1,238.20 msで、既存の1,500 ms目安内だった。`NEXT-START-001`の新規発行先初回は、LibVLC初期化11,780.21 msが`Show`より前にあったため完全初期化まで13,280.22 msかかった。改善後も初回native load自体は11,014.18 ms残るが、空シェルは1,238.20 msで先に表示され、Windowの描画と入力をブロックしない。

反復時の完全初期化中央値は1,027.79～1,080.40 msで、ファイル引数の初回要求も中央値54.01 msを維持した。最大の中央値寄与は`Show` 304.15 ms、Window生成279.46 ms、LibVLC初期化182.48 ms、Show返却から`ContentRendered`まで63.98 ms、動画プロファイル初期化22.53 msである。永続Repositoryの区間は並行しているため合算しない。

## 3. 終了と回帰確認

- 最終の3条件×5回は完全な計測レポートを生成し、15/15プロセスが通常終了した。
- ファイル引数条件を計測直後2秒で閉じる人工条件では、動画出力・サムネイル停止と重なる30秒超過を1回観測した。5秒安定待ちの追加3/3と最終5/5は正常終了した。この待ちは起動計測値には含まれない。
- 別の新規発行先を空起動し、シェル表示500 ms後かつLibVLC初期化中に終了要求を送った。シェル1,259.45 ms、LibVLC初期化11,068.30 ms、終了開始12,491.81 msを記録し、生成済みnative資源を破棄して30秒以内・終了コード0で終了した。
- 初回要求と二次IPC要求はサービス接続前に処理せず、既存の有界FIFOキューへ保持する。初期要求完了後にだけ自動更新確認を開始する順序も維持した。

## 4. 確定した数値目標

- 新規発行先初回を含む空シェル操作可能: 各5回すべて1,500 ms以内。
- 同一発行物の反復時完全初期化: 空起動・ファイル引数起動とも各5回すべて1,500 ms以内。
- 新規発行先初回の完全初期化はnative load約11秒をバックグラウンドで継続するため、空起動の合否には使わない。ファイル引数起動では初期化完了後に自動再生し、要求順序と既存の再生準備性能を維持する。

この目標は今回の実測で満たしている。開発者は2026-08-30に数値目標と、新規発行先初回では再生機能だけが後から有効になる挙動を承認し、`NEXT-START-002`を完了とした。
